摘要

中小餐饮、零售及服务业团队普遍缺少专用排班系统，主要依赖纸张或 Excel 管理班次，存在排班冲突靠人工发现、员工可用时间难以记全、全职与兼职工时规则混用、工时汇总繁琐易错等问题。针对上述痛点，本项目设计并实现了轻量级排班与工时统计工具“轻排班”，服务店长（排班负责人）完成员工与班次模板管理、周视图排班编制与调整、排班冲突检测、工时统计和 Excel 报表导出的完整业务流程。

系统采用 Python + Flask + SQLite 技术路线，前端按 Material 3（Material You）设计语言自行实现米 beige 视觉主题；核心的冲突检测与工时计算以纯函数模块实现，支持班次重叠、可用时间冲突、班间休息不足、每日/每周工时上限五类可配置规则，并正确处理跨日班次与统计周期边界。目前项目已完成可运行原型：58 项单元与功能测试全部通过，开发环境实测主要页面响应 P95 不超过 40 毫秒、报表导出 P95 不超过 110 毫秒；演示数据中的三类埋设冲突全部被系统检出。系统已内置管理员密码登录（PBKDF2 加盐哈希、失败限速、可改密）；员工自助查看等扩展功能列为后续计划。

关键词：排班管理；工时统计；冲突检测；Flask；SQLite；Material 3

1 引言

1.1 研究背景

在餐饮、零售及生活服务行业，5～30 人规模的门店数量庞大。此类团队的排班通常由店长或值班经理一人承担：先用 Excel 或纸质表排出下一周班次，再截图发到员工微信群。这一流程能够运转，但高度依赖店长的个人经验与记忆力——每位员工的兼职课时、上课时间、请假习惯都装在“脑子里”，换人就断档。

与排班相伴的工时统计同样依赖手工：月底把每个人的班次逐条相加，扣除班内休息，再区分全职与兼职口径。过程重复、繁琐，且一旦出现跨日班次或临时调班，人工计算极易出错，也难以追溯核对。

1.2 问题描述

通过对手工/Excel 排班流程的逐环节分析，可归纳出四类典型问题：

问题具体表现后果
冲突不易发现同一员工两班时间重叠、与已约定的不可用时间冲突、相邻班次间隔过短等，靠人工逐格核对，排除干扰大且易漏检班表发布后返工，现场人手冲突或员工临时拒班
约束难以记全员工可用时间各异（学生兼职尤其明显），约束信息分散在聊天记录中排班反复修改，沟通成本高
规则口径不一全职与兼职适用不同的每日/每周工时上限，Excel 无法按用工类型自动区分控制兼职工时被动超标，机构合规风险上升
汇总繁琐易错跨日班次、休息扣除、周/月边界等细节需人工处理，月底统计耗时工时争议缺乏可核对依据

大型企业的人力资源系统覆盖了上述需求，但对小团队而言存在部署重、费用高、功能冗余的问题；通用表格工具又缺乏业务约束。中小团队需要的是一件“趁手的轻工具”。

1.3 研究目标与意义

本项目目标是设计并实现一个面向小规模团队、可本地部署的排班与工时统计工具，完整覆盖“维护员工与班次基础数据 → 编制与调整排班 → 冲突检测与提示 → 工时自动汇总 → 报表导出”的业务闭环。其意义在于：

  • 提高排班效率：周视图网格直接点选排班，常用班次一键套用模板；
  • 辅助控制风险：五类冲突规则自动检测并解释原因，错误级冲突在保存前强制确认；
  • 工时可信可核：统计由排班记录实时推导，口径统一（跨日归属、休息扣除、周期边界均有明确定义），并支持导出 Excel 留档；
  • 改善信息获取：周表一键导出张贴或转发，员工无需翻聊天记录。

1.4 项目范围

本项目面向单店小团队（约 5～50 人），定位为本阶段可运行、可演示、可检查的技术原型。范围边界如下：

  • 已包含：员工管理、班次模板、排班编制与调整、冲突检测、工时统计、Excel 导出、规则配置、数据库备份（详见第 2 章需求清单及各条实现状态）；
  • 本阶段不包含：员工账号登录与移动端自助查看、考勤打卡、薪资计算、多门店管理、自动排班算法——均未实现，仅在总结与展望中作为后续工作说明；
  • 合规说明：工时上限、休息间隔等规则在本系统中均为可配置项，随附默认值仅作演示口径；正式使用前，机构应按其所在地区适用的法律法规及自身用工形式确认具体设置，本工具的提示不构成合规结论。

2.3 冲突检测规则需求

冲突规则全部设计为可配置项（设置页可改，存于数据库 settings 表），默认值仅作演示口径：

编号规则级别判定逻辑与默认值
R1班次重叠错误同一员工两个班次的有效时间区间交集大于 0 分钟即触发，提示重叠时长及对方班次信息
R2可用时间冲突错误排班日不在员工“可排班日”集合内，或班次起止超出“每日可用时段”，即触发；两者均可按员工配置
R3班间休息不足提示同一员工前后两个班次之间间隔低于最小休息间隔（默认 600 分钟 = 10 小时），提示实际间隔
R4每日工时上限提示当日有效工时合计超过按用工类型配置的上限（默认全职 600 分钟、兼职 480 分钟），提示合计值
R5每周工时上限提示本周（周一至周日）有效工时合计超过按用工类型配置的上限（默认全职 2640 分钟 = 44 小时、兼职 1440 分钟 = 24 小时），提示合计值

错误级冲突（R1、R2）阻断保存流程，对话框中给出“返回修改”与“仍要保存”两个出口，避免误操作同时保留门店特殊安排的灵活性；提示级冲突（R3、R4、R5）可直接保存，但在冲突面板与班次芯片上持续可见。为避免同一条件随班次数量重复刷屏，展示层对 R3/R4/R5 按“员工+日期/周期”去重。

3 系统设计

3.1 总体架构

系统采用经典三层结构，核心业务逻辑独立成纯函数模块，与 Web 框架解耦：

表现层
Jinja2 服务端模板（6 个页面）+ 原生 CSS（Material 3 米 beige 主题）+ 原生 JavaScript（对话框、提交与冲突确认、提示条）
▲ HTTP（HTML / JSON）
应用层
Flask 路由：6 个页面路由 + 排班 JSON API（POST/PUT/DELETE /api/schedules、GET /api/conflicts）+ 导出与备份端点；输入校验、冲突确认流程（409 → force 重提交）
▲ 函数调用
业务核心
core/scheduling.py 时间区间与冲突检测
core/worktime.py 工时汇总
core/exporter.py Excel 生成
数据层
SQLite 单文件数据库（employees / shift_templates / schedules / settings 四表）
db.py 连接与初始化

图 3-1 系统分层架构（文字示意）

主要数据流：排班页加载时，应用层读取该周排班与相邻班次，调用 check_conflicts 计算冲突并在服务端渲染进网格与冲突面板；保存排班时，前端以 JSON 提交，应用层校验后调用同一冲突检测函数，存在错误级冲突则返回 409 与冲突明细，用户确认后携带 force 标志重新提交方可落库。读取与写入共用同一套规则实现，保证“检测口径 = 展示口径”。

3.2 技术选型

技术版本选择理由
Python3.14语法简洁、标准库完善，适合快速构建原型；团队学习成本低
Flask3.1轻量 Web 框架，路由/模板/测试支持齐备，无需脚手架即可运行，匹配“轻量单店工具”定位
SQLite3（标准库 sqlite3）零配置、单文件、事务完整；单店单机场景无需独立数据库服务，备份即复制文件
Jinja2 + 原生 CSS/JS3.1 / ES2020服务端渲染减少前后端联调成本；Material 3 无官方轻量 Web 组件且比赛环境可能离线，故按 M3 设计令牌（token）自行实现组件样式，不引入构建工具与运行时依赖
openpyxl3.1纯 Python 写入 .xlsx，支持合并单元格、填充色等样式，满足报表美化需求
pytest9.1参数化与夹具机制成熟，适合对纯函数核心做密集单元测试

选型限制说明：Flask 开发服务器为单线程参考实现，原型按单用户设计，未做并发控制与生产部署加固；若后续多用户使用，应更换生产级 WSGI 服务器并增加认证层。

3.3 数据库设计

共 4 张表：员工（employees）、班次模板（shift_templates）、排班记录（schedules）、规则配置（settings）。完整 DDL 见附录 A。

表主要字段说明
employees
（员工）		id(PK)、name、position、employment_type(fulltime/parttime)、phone、available_days(JSON 数组，ISO 星期 1–7)、available_from/to、status(active/inactive)、note、created_at可用时间用于冲突检测；时薪等敏感字段按最小化收集原则未纳入
shift_templates
（班次模板）		id(PK)、name、start_time、end_time(早于开始即跨日)、break_minutes、position、color(芯片配色 token)、note常用班次的可复用定义
schedules
（排班记录）		id(PK)、employee_id(FK→employees)、work_date(开始日期)、start_time、end_time、break_minutes、position、template_id(FK→shift_templates, ON DELETE SET NULL)、note、created_at班次时间在创建时保存快照，模板删除不影响历史排班；索引 (employee_id, work_date) 与 (work_date) 支撑周查询
settings
（规则配置）		key(PK)、value门店名称、最小休息间隔、四项工时上限等键值对，界面可改

实体关系：employees 1—N schedules；shift_templates 1—N schedules（弱关联，置空不级联删除）。

设计决策一（工时不单独建表）：工时统计由排班记录实时推导而非落库。排班是工时的唯一数据源，推导式统计天然避免“排班已改、工时未同步”的双写不一致；若后续接入考勤打卡，再引入实际工时表与“计划/实际”对照，属扩展方向。

设计决策二（跨日归属）：跨日班次整体归属开始日期所在的日/周/月统计周期。该规则在冲突检测（周上限）与工时统计两处一致执行，并在界面文案中明示。

3.4 核心模块设计

3.4.1 排班模块

排班编制围绕周视图网格展开：行=在职员工（含岗位与用工类型），列=周一至周日。新增班次流程为：点击空白格 → 对话框自动带入员工与日期 → 选择模板自动填充时段与休息（或自定义时间）→ 前端基础校验 → 提交 JSON API → 服务端校验与冲突检测 → 无错误级冲突直接保存，有则返回 409 由用户确认。调整与删除通过点击既有班次芯片进入同一对话框完成，编辑时冲突检测自动排除自身记录。

3.4.2 冲突检测模块

检测函数 check_conflicts(候选排班, 该员工既有排班, 员工约束, 规则配置) 为纯函数，输入输出均为值对象，判定步骤：

  1. 把“日期 + 起止时间”展开为绝对时间区间（结束早于等于开始视为次日结束），计算候选班次的有效工时；
  2. R1 重叠：对每条既有班次求区间交集，交集 > 0 分钟即产出错误级冲突，消息含对方班次与重叠分钟数；
  3. R2 可用时间：候选日期的 ISO 星期不在集合内，或起止超出每日可用时段，产出错误级冲突；
  4. R3 班间休息：分别找候选班次之前最近结束、之后最近开始的班次（跳过已判重叠者），间隔低于配置值即产出提示；
  5. R4/R5 工时上限：按“开始日期”归集当日/当周（周一至周日）全部既有班次的有效工时，加候选值后与按用工类型选取的上限比较，超出即产出提示；
  6. 返回冲突列表（规则、级别、含具体数字的中文消息、关联班次 id），由页面/API 层决定渲染方式与是否阻断。

3.4.3 工时统计模块

统计口径统一为：有效工时 = 班次跨度 − 班内休息（跨度按跨日规则展开）；跨日班次整体归属开始日期所在周期；周定义为周一至周日，月为自然月。汇总函数对区间内排班逐条累加，输出每人的班次数、排班时长、休息时长、有效工时与逐日明细（用于周视图的逐日列与导出）。统计与冲突检测共用同一组时间函数，口径一致。

3.4.4 导出模块

4.4 核心代码说明

4.4.1 时间区间展开与有效工时（core/scheduling.py）

def shift_span_minutes(start_hhmm: str, end_hhmm: str) -> int:
    """班次跨度（分钟），跨日自动加 24 小时；起止相同视为非法。"""
    start, end = parse_hhmm(start_hhmm), parse_hhmm(end_hhmm)
    if start == end:
        raise ValueError("班次开始与结束时间相同")
    span = end.hour * 60 + end.minute - (start.hour * 60 + start.minute)
    if span < 0:
        span += 24 * 60
    return span

def effective_minutes(start_hhmm, end_hhmm, break_minutes) -> int:
    """有效工时（分钟）= 跨度 − 休息时长，下限 0。"""
    return max(0, shift_span_minutes(start_hhmm, end_hhmm) - int(break_minutes or 0))

def shift_datetime_range(work_date, start_hhmm, end_hhmm):
    """把“日期 + 起止时间”展开为绝对时间区间，跨日结束时间落到次日。"""
    start = datetime.combine(work_date, parse_hhmm(start_hhmm))
    end = datetime.combine(work_date, parse_hhmm(end_hhmm))
    if end <= start:
        end += timedelta(days=1)
    return start, end

这三个函数是全部口径的基础：跨度计算允许“19:00–01:00”式跨日班次；有效工时统一扣除休息；区间展开把班次映射到绝对时间轴，供重叠与间隔判定使用。起止相同被显式拒绝，避免出现“24 小时班次”的二义性。

防错与恢复表单校验前置（时间格式、起止相同、越界）；错误级冲突强制二次确认；删除班次有确认框且可重新添加恢复
一致性同一套按钮/芯片/对话框样式贯穿 6 个页面；日期、时间、工时格式统一
效率模板一键套用；周导航与“本周”快捷键位；概览页直达高频操作
可及性状态不只靠颜色（图标+文字）；焦点可见；网格支持键盘操作

局限：以上为开发者自查结论，尚未开展真实用户参与的任务计时、满意度问卷或与 Excel 流程的对照实验；相关测试条件、对象与指标已在附录 C 中作为需求验证计划列出，本报告不虚构此类对比数据。

5.6 已知简化与局限

  • 重叠班次工时重复计入：当错误级重叠已存在时，日/周工时按记录逐条累加，重叠时段会被重复计入合计；系统通过 R1 规则显著标出重叠以便人工核实，未做去重合并；
  • 单账号、无并发控制：已实现管理员密码登录（会话 7 天），但按单店长使用设计，无多账号与并发写保护；
  • 无操作审计：调班、删除暂无历史留痕（数据库备份可作时点恢复）；
  • 开发服务器：未做生产部署加固（HTTPS、WSGI 服务器、进程守护）；
  • 可用时段仅支持“每日一段”窗口：不支持同一员工一天内多段可用时间，跨日班次与窗口组合存在场景限制（如跨日班次必超当日窗口，需为夜班员工留空时段约束）。

6 总结与展望

6.1 工作总结

本项目完成了一个面向中小团队排班场景的完整技术原型，主要工作包括：

  • 需求层面：从手工/Excel 排班的四个具体痛点出发，定义了 7 项功能需求、5 类可配置冲突规则与相称的非功能需求，明确了本阶段范围边界；
  • 设计层面：完成三层架构与 4 表数据库设计；确立“排班记录为工时唯一数据源”“跨日归开始日期”“错误级阻断/提示级可见”三项关键设计决策；按 Material 3 规范建立米 beige 设计令牌体系并落地为可复用组件样式；
  • 实现层面：交付可运行的 Flask + SQLite 原型（约 3400 行源码），覆盖员工管理、班次模板、周视图排班、五类冲突检测、日/周/月工时统计、Excel 报表导出、规则配置、备份与管理员密码登录；核心逻辑以纯函数实现，与框架解耦；
  • 验证层面：58 项自动化测试全部通过（含登录保护、错误密码、改密校验、限速等认证场景），覆盖正常排班、重叠、不可用时间、工时上限、跨日、休息扣除、周期边界与导出等竞赛要求场景；以脚本实测原型规模下页面响应 P95 ≤ 40 毫秒、导出 P95 ≤ 110 毫秒；
  • 成果物：可运行软件与源代码、技术研究报告（本文）、9 张真实运行截图、性能测量记录、演示视频脚本（附录 D）。

6.2 不足

原型仍有明显局限：单管理员账号、无员工自助与分角色权限；重叠时段工时重复计入；无操作审计；可用时段仅支持每日一段；未开展真实用户评估与并发测试。上述已在 5.6 节如实说明，均不影响本阶段功能验证的有效性。

PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS employees (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    name            TEXT    NOT NULL,
    position        TEXT    NOT NULL DEFAULT '',
    employment_type TEXT    NOT NULL DEFAULT 'fulltime',   -- fulltime / parttime
    phone           TEXT    NOT NULL DEFAULT '',
    available_days  TEXT    NOT NULL DEFAULT '[1,2,3,4,5]', -- JSON：ISO 星期 1–7
    available_from  TEXT    NOT NULL DEFAULT '',            -- HH:MM，空为不限
    available_to    TEXT    NOT NULL DEFAULT '',
    status          TEXT    NOT NULL DEFAULT 'active',      -- active / inactive
    note            TEXT    NOT NULL DEFAULT '',
    created_at      TEXT    NOT NULL DEFAULT (datetime('now','localtime'))
);

CREATE TABLE IF NOT EXISTS shift_templates (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    name          TEXT    NOT NULL,
    start_time    TEXT    NOT NULL,
    end_time      TEXT    NOT NULL,        -- ≤ start 表示次日结束（跨日）
    break_minutes INTEGER NOT NULL DEFAULT 0,
    position      TEXT    NOT NULL DEFAULT '',
    color         TEXT    NOT NULL DEFAULT 'primary',
    note          TEXT    NOT NULL DEFAULT ''
);

CREATE TABLE IF NOT EXISTS schedules (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    employee_id   INTEGER NOT NULL REFERENCES employees(id),
    work_date     TEXT    NOT NULL,        -- YYYY-MM-DD（班次开始日期）
    start_time    TEXT    NOT NULL,
    end_time      TEXT    NOT NULL,
    break_minutes INTEGER NOT NULL DEFAULT 0,
    position      TEXT    NOT NULL DEFAULT '',
    template_id   INTEGER REFERENCES shift_templates(id) ON DELETE SET NULL,
    note          TEXT    NOT NULL DEFAULT '',
    created_at    TEXT    NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_schedules_emp_date ON schedules(employee_id, work_date);
CREATE INDEX IF NOT EXISTS idx_schedules_date     ON schedules(work_date);

CREATE TABLE IF NOT EXISTS settings (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

工时数据不单独建表：由 schedules 按统计周期实时推导（设计决策见 3.3）。规则默认值：最小休息间隔 600 分钟；全职日/周上限 600/2640 分钟；兼职日/周上限 480/1440 分钟——均为演示口径，须按当地法规与机构制度调整。
