摘要

中小餐饮、零售及服务业团队普遍缺少专用排班系统，主要依赖纸张或 Excel 管理班次，存在排班冲突靠人工发现、员工可用时间难以记全、全职与兼职工时规则混用、工时汇总繁琐易错等问题。针对上述痛点，本项目设计并实现了轻量级排班与工时统计工具“轻排班”，服务店长（排班负责人）完成员工与班次模板管理、周视图排班编制与调整、排班冲突检测、工时统计和 Excel 报表导出的完整业务流程。

系统采用 Python + Flask + SQLite 技术路线，前端按 Material 3（Material You）设计语言自行实现米 beige 视觉主题；核心的冲突检测与工时计算以纯函数模块实现，支持班次重叠、可用时间冲突、班间休息不足、每日/每周工时上限五类可配置规则，并正确处理跨日班次与统计周期边界。目前项目已完成可运行原型：58 项单元与功能测试全部通过，开发环境实测主要页面响应 P95 不超过 40 毫秒、报表导出 P95 不超过 110 毫秒；演示数据中的三类埋设冲突全部被系统检出。系统已内置管理员密码登录（PBKDF2 加盐哈希、失败限速、可改密）；员工自助查看等扩展功能列为后续计划。

关键词：排班管理；工时统计；冲突检测；Flask；SQLite；Material 3

1 引言

1.1 研究背景

在餐饮、零售及生活服务行业，5～30 人规模的门店数量庞大。此类团队的排班通常由店长或值班经理一人承担：先用 Excel 或纸质表排出下一周班次，再截图发到员工微信群。这一流程能够运转，但高度依赖店长的个人经验与记忆力——每位员工的兼职课时、上课时间、请假习惯都装在“脑子里”，换人就断档。

与排班相伴的工时统计同样依赖手工：月底把每个人的班次逐条相加，扣除班内休息，再区分全职与兼职口径。过程重复、繁琐，且一旦出现跨日班次或临时调班，人工计算极易出错，也难以追溯核对。

1.2 问题描述

通过对手工/Excel 排班流程的逐环节分析，可归纳出四类典型问题：

问题具体表现后果
冲突不易发现同一员工两班时间重叠、与已约定的不可用时间冲突、相邻班次间隔过短等，靠人工逐格核对，排除干扰大且易漏检班表发布后返工，现场人手冲突或员工临时拒班
约束难以记全员工可用时间各异（学生兼职尤其明显），约束信息分散在聊天记录中排班反复修改，沟通成本高
规则口径不一全职与兼职适用不同的每日/每周工时上限，Excel 无法按用工类型自动区分控制兼职工时被动超标，机构合规风险上升
汇总繁琐易错跨日班次、休息扣除、周/月边界等细节需人工处理，月底统计耗时工时争议缺乏可核对依据

大型企业的人力资源系统覆盖了上述需求，但对小团队而言存在部署重、费用高、功能冗余的问题；通用表格工具又缺乏业务约束。中小团队需要的是一件“趁手的轻工具”。

1.3 研究目标与意义

本项目目标是设计并实现一个面向小规模团队、可本地部署的排班与工时统计工具，完整覆盖“维护员工与班次基础数据 → 编制与调整排班 → 冲突检测与提示 → 工时自动汇总 → 报表导出”的业务闭环。其意义在于：

  • 提高排班效率：周视图网格直接点选排班，常用班次一键套用模板；
  • 辅助控制风险：五类冲突规则自动检测并解释原因，错误级冲突在保存前强制确认；
  • 工时可信可核：统计由排班记录实时推导，口径统一（跨日归属、休息扣除、周期边界均有明确定义），并支持导出 Excel 留档；
  • 改善信息获取：周表一键导出张贴或转发，员工无需翻聊天记录。

1.4 项目范围

本项目面向单店小团队（约 5～50 人），定位为本阶段可运行、可演示、可检查的技术原型。范围边界如下：

  • 已包含：员工管理、班次模板、排班编制与调整、冲突检测、工时统计、Excel 导出、规则配置、数据库备份（详见第 2 章需求清单及各条实现状态）；
  • 本阶段不包含：员工账号登录与移动端自助查看、考勤打卡、薪资计算、多门店管理、自动排班算法——均未实现，仅在总结与展望中作为后续工作说明；
  • 合规说明：工时上限、休息间隔等规则在本系统中均为可配置项，随附默认值仅作演示口径；正式使用前，机构应按其所在地区适用的法律法规及自身用工形式确认具体设置，本工具的提示不构成合规结论。

2 需求分析

2.1 用户角色

角色职责与需求本阶段状态
店长 / 排班负责人维护员工档案与班次模板；创建、查看、调整周排班；查看冲突提示并处理；查看工时统计并导出报表；配置排班规则与数据备份已实现（管理员密码登录，单账号）
普通员工查看本人排班与工时信息、提交可用时间本阶段未实现账号体系；员工目前通过导出的周表获取排班信息。员工自助查看已列为后续扩展（见 6.4），不属于已完成功能

2.2 功能需求

编号需求说明状态
FR1员工信息管理姓名、岗位、全职/兼职类型、联系方式、可排班日与每日可用时段、在职状态、备注；支持新增、编辑、删除（有排班记录者转为停用以保留历史）已实现
FR2班次模板管理班次名称、开始/结束时间（支持跨日）、班内休息分钟、建议岗位、芯片配色；排班时可一键套用已实现
FR3排班管理以周为单位浏览排班网格（行=员工、列=周一至周日）；点击空格新增、点击班次芯片编辑/删除；支持上一周/本周/下一周导航已实现
FR4排班冲突检测检测班次重叠、可用时间冲突、班间休息不足、每日/每周工时超限五类情况，逐条解释原因；错误级冲突保存前需二次确认（详见 2.3）已实现
FR5工时统计按日/周/月汇总每位员工的班次数、排班时长、休息时长、有效工时，含逐日明细；统一处理休息扣除、跨日班次归属与统计周期边界已实现
FR6报表导出排班表（日期、星期、员工、岗位、时段、休息、有效工时、备注）与工时统计表（含逐日列与合计行）导出为 .xlsx 文件已实现
FR7数据与权限管理数据本地存储于单一 SQLite 文件，支持一键下载备份；系统标题与品牌头像可在设置页自定义（同步用于侧边栏、浏览器标签与站点图标）；冲突规则可在设置页调整。已实现单管理员密码登录（PBKDF2 哈希存储、登录失败限速、设置页改密、登出）；员工自助账号与分角色权限未实现，见展望部分实现

2.3 冲突检测规则需求

冲突规则全部设计为可配置项（设置页可改，存于数据库 settings 表），默认值仅作演示口径：

编号规则级别判定逻辑与默认值
R1班次重叠错误同一员工两个班次的有效时间区间交集大于 0 分钟即触发，提示重叠时长及对方班次信息
R2可用时间冲突错误排班日不在员工“可排班日”集合内，或班次起止超出“每日可用时段”，即触发；两者均可按员工配置
R3班间休息不足提示同一员工前后两个班次之间间隔低于最小休息间隔（默认 600 分钟 = 10 小时），提示实际间隔
R4每日工时上限提示当日有效工时合计超过按用工类型配置的上限（默认全职 600 分钟、兼职 480 分钟），提示合计值
R5每周工时上限提示本周（周一至周日）有效工时合计超过按用工类型配置的上限（默认全职 2640 分钟 = 44 小时、兼职 1440 分钟 = 24 小时），提示合计值

错误级冲突（R1、R2）阻断保存流程，对话框中给出“返回修改”与“仍要保存”两个出口，避免误操作同时保留门店特殊安排的灵活性；提示级冲突（R3、R4、R5）可直接保存，但在冲突面板与班次芯片上持续可见。为避免同一条件随班次数量重复刷屏，展示层对 R3/R4/R5 按“员工+日期/周期”去重。

2.4 非功能需求

维度需求（与原型规模相称）
易用性全中文界面；主要操作（新增班次、调整排班、查看冲突、导出报表）一键可达；表单有明确标签与校验；空状态、操作成功/失败均有可见反馈（提示条、空状态插画位、冲突面板）
